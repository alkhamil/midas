# Performance baseline

Measure only: nothing was optimised. Generated by `node scripts/perf-baseline.mjs --mode headless|headed`, from seeded documents of mixed frames, text, rectangles, ellipses and strokes with gradient paints (one large screen, the rest 100-layer screens). Cells are **p50 / p95**. A frame interval is the time between animation frames while the scenario runs: 16.7 ms is 60 fps, a frame that costs more stretches it. Input latencies run from the input event to the second painted frame after it. The studio is the Vite dev server (unminified, so the hotspot names are the source functions).

## Reading the results

- **Frame interval** is capped by the display refresh: 16.7 ms is 60 Hz, so a p50 of 16.7 means the frame fit its budget and a p95 of 33 or more is a dropped frame. Pan, zoom and drag saturate at the cap at these sizes; the p95 is where cost shows.
- **Headless** uses the Canvas 2D fallback on software rendering (WebGPU is exposed but returns no adapter). **Headed** is Chrome with a window: WebGPU on the machine's integrated Intel Iris Xe (not a discrete GPU), so the numbers say what a laptop with an integrated GPU does.
- **Enter Play** is the large screen (up to 2000 layers) mounted as DOM plus `toDomTree` over the whole document, so it grows with both. **Hover and press** are on a Button on its own frame: about two frames of input latency, independent of the document size here.
- **Hotspots** are self time over the whole measured session (every scenario, plus the Generate Design System that makes the Button), so `tokens.js` dominates at 1k and `toDataURL` at 5k and 20k. `toDataURL` is canvas read-back; the likely source in Play is the raster of each angular or diamond stroke (the generated document has many, each at its own size), which the Rust-core stroke work added. It was not isolated by a profile without them.
- One run per size, no repeat: treat differences under about 10% as noise.
